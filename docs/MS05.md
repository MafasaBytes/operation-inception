# MS05 — Procedural game-audio foundation

## Research question and scope

Can short, related team sounds make placements, increasing charge, explosions,
captures, cascade escalation, elimination, and victory distinguishable on a phone
without explanatory speech? Does rising event intensity support anticipation and
resolution without harshness or fatigue? These are listening questions, not
conclusions from finite PCM or distinct spectra.

This slice contains an immutable timed-event contract, one **synthetic** two-team
fixture, sample-based procedural synthesis, one WAV, and focused tests. MS04 is
not implemented. The fixture demonstrates event sounds; it is neither a genuine
match nor a complete legal board-state history. Its illustrative precharged cells
must not be treated as an engine test oracle or a fabricated product match.

## Audio-event contract, version 1

`fixtures/ms05/two-team-v1.json` uses schema `ms05.audio-events.v1`, log ID
`ms05.synthetic.two-team.v1`, `synthetic: true`, a 12-second output window,
two teams, and 43 events. Parsing creates frozen `Team`, `AudioEvent`, and
`EventLog` dataclasses containing tuples; mutable JSON metadata is not retained.

| Field | Contract |
| --- | --- |
| `schema_version`, `log_id`, `synthetic` | Explicit version, identity, and provenance; unknown versions fail |
| `duration_seconds` | Absolute presentation/output window, including cue release; truncating a cue is an error |
| `teams` | Two to eight unique string IDs, each assigned a distinct voice index 0–7 |
| Event `id`, `sequence` | Unique stable identity and strictly increasing order; same-time events use sequence order |
| `time_seconds` | Finite nonnegative absolute time from presentation start; nondecreasing in the log |
| `kind`, `team_id` | Known semantic fact and team; no sound names or frame numbers |
| `cell` | Optional immutable `(row, column)` context; audio does not validate board rules or use it as a clock |
| `orb_count`, `critical_mass` | Counts supplied by the producer; required for charge/critical cues |
| `cascade_depth` | Nonnegative local cascade depth supplied by MS04; zero is the origin |
| `previous_team_id` | Previous owner for a capture, or null for previously unowned territory |
| `metadata` | Informational JSON annotations only; display FPS never changes audio |

The affected/acting team is `team_id`; for `neighbor_captured` it is the incoming
owner, for danger/elimination the endangered/eliminated team, and for victory the
winner. The audio system never derives elimination or victory from cell counts.
It checks event structure and references, not legal moves or game-state truth.
It accepts excess `orb_count` values and does not choose an excess-orb rule.

Supported events and intended cues:

| Event kind | Intended cue |
| --- | --- |
| `turn_started` | Quiet, short team cue |
| `orb_placed` | Short placement impact |
| `cell_charged` | Higher pitch, level, and pulse density as count approaches threshold |
| `cell_became_critical` | Distinct two-pulse threshold cue |
| `cell_exploded` | Percussive transient; pitch, level, and pulse density rise with depth |
| `neighbor_captured` | Incoming team's capture sound |
| `cascade_depth_increased` | Brief escalation tick, separate from the explosion |
| `player_endangered` | Short tension punctuation in that team's family |
| `player_eliminated` | Falling, lower punctuation in the eliminated team's family |
| `winner_declared` | Stable two-pulse resolution in the winning team's family |

In this fixture, “became critical” means threshold reached, preceding explosion.
The charge cue below that threshold communicates approach. MS04 must confirm
this naming/ordering or version the contract before integration.

## Fixture listening map

At 0.55 and 1.55 s, hear the two placement identities separately. Repeated
placements and charges follow through 7.55 s. A small corner explosion occurs
at 8.27 s; its capture at 8.31 s changes an orange cell to cyan. The orange
five-step cascade has explosions at 8.97, 9.21, 9.40, 9.56, and 9.69 s, depths
0–4. Its 9.73 s recapture reverses ownership of that same cell back to orange.
Elimination is at 10.10 s and the winning resolution at 10.55 s. These are
synthetic audio examples, not claims about a simulated match.

## Team identity strategy

Eight fixed voices share damped oscillator/noise construction and related pitch
registers. Voice 0 (cyan in the fixture) has a bright 659.255 Hz placement root;
voice 1 (orange) uses 329.628 Hz with a stronger second partial. The other voices
use distinct roots at 523.251, 261.626, 783.991, 391.995, 587.330, and 293.665 Hz,
with different partial weights. This supports two to eight identities without
speech, instrument samples, or a model. The game assigns IDs; the sound system
maps them to voices. It does not know how the game chooses a team or a winner.

Pitch, pulse count, and isolated cue RMS increase with cascade depth. In the
fixture's five-step chain, pre-pan RMS levels are 0.085, 0.102, 0.119, 0.136,
and 0.153, with one through five pulses. This is a designed/measured progression;
its perceived escalation and eight-way identity recognition remain unvalidated.
Depth above eight reaches a sonic ceiling without limiting game depth.

## Timing, mixing, and reproducibility

Synthesis consumes the complete immutable log after offline simulation. Future
MS04 pure rules may emit logical events first; a deterministic presentation-time
mapper must assign absolute seconds before MS05 consumes them. Animation can
sample that same clock at any FPS. No game engine or renderer is imported here.

Events begin at the nearest sample, with positive half-sample ties rounded up.
There is no FPS argument, frame rounding, or video dependency. Cues use per-event
PCG64 noise seeds derived from the audio seed, schema version, and stable event ID.
An unchanged event log/seed reproduces PCM in the same numerical environment;
the manifest records Python/NumPy versions and source/fixture/PCM/WAV hashes.
Cross-platform bit identity is not promised across numerical library changes.

Mixing uses float64, mild fixed team panning, and identical phase in both channels.
No stereo delay, phase inversion, or reverb is used. Mono is the amplitude
downmix, so team identity must survive without spatial separation. One constant
attenuation reserves a 0.86 sample-peak ceiling if needed; the system does not
boost quiet mixes or hide clipping with distortion. Final output is 16-bit PCM,
48 kHz stereo by default; mono and 16–96 kHz rates are supported. The manifest
reports actual peak, gain, per-channel RMS, and each cue's sample onset/parameters.

There is no loudness-target mastering or continuous-time true-peak meter. Many
simultaneous events can make a whole mix quieter under shared attenuation; dense
real-match scheduling and event priorities need later evaluation. Tail truncation
is rejected rather than silently cutting off a winner cue.

## Explicit voiceover exclusion

No generated speech, narration, voiceover, music track/bed, LLM, Hugging Face
model, or generative model is used. All sounds are event-triggered effects.
“Trust your instinct. Pick a color.” is external production material to record
or add later in TikTok Studio. Neither rendering nor audio code/fixture includes
that hook. There is no publishing or TikTok API integration.

## Run and acceptance

```bash
.venv/bin/python -m inception.audio --events fixtures/ms05/two-team-v1.json --seed 505 --output outputs/ms05/ms05-fixture-v1.wav
.venv/bin/python -m pytest -q tests/test_ms05_audio.py
.venv/bin/python tools/verify_particle_freeze.py
```

The WAV command refuses an existing WAV or manifest. Choose a fresh filename
instead of overwriting prior work. Generated files are ignored under `outputs/`.

Technical checks cover immutable input, exact repeated PCM/WAV, seed sensitivity,
24/60 FPS annotation independence, off-frame sample onsets at 24/48 kHz, finite
unclipped output, mono compatibility, two-to-eight distinct voice spectra,
increasing charge/cascade energy, invalid contracts, and release-tail protection.

Creative acceptance is pending normal-speed phone listening, including mono:
can listeners distinguish the two teams, placement versus explosion/capture,
rising charge/cascade intensity, elimination versus winning resolution, and an
event rhythm without harshness or fatigue? Eight-team use and actual game context
are later checks. Technical success does not establish satisfaction or attention.

## MS04 decisions before integration

Confirm grid coordinates and neighbor order; excess-orb handling; queue versus
wave cascade ordering and local depth definition; when ownership changes; when
elimination protection ends; victory after cascade completion; and deterministic
handling of repeated states/non-termination. MS05 must not supply those rules.
Agree event granularity/unique IDs, same-time ordering, critical-event semantics,
logical-event-to-seconds mapping, tail allowance, and two-to-eight team/voice
assignments. Future match selection must use genuine complete game logs rather
than the synthetic fixture or a scripted winning color. See [ROADMAP](ROADMAP.md).
